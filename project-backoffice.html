1. 주제 선정 배경

6인 팀으로 진행한 이커머스 관리자용 백오피스 백엔드 프로젝트입니다. 수많은 주문과 상품 데이터가 누적되는 관리자 환경에서 대용량 주문 데이터의 조회 성능 개선과 주문 상태 정합성 확보에 집중하여, 관리자 운영 효율성과 시스템 안정성을 향상시키는 것을 목표로 기획했습니다.

2. 담당 역할

  • 주문 상태 관리, 주문 취소, 관리자 대시보드 백엔드 API 설계 및 구현 담당
  • 실행 계획 분석 및 복합 인덱스(Covering Index) 설계를 통한 대시보드 쿼리 성능 최적화
  • 주문 상태 전이 검증 로직 적용 및 상태 관리 일원화
  • Soft Delete 예외 처리 및 CommonException 기반 공통 예외 체계 표준화 구축

3. 기술 스택

  • 주문 상태 관리: 상태 변경 규칙(결제완료 → 배송준비 → 배송중 → 배송완료 등) 강제를 통한 비정상 전이 차단

6. 기술적 의사결정 및 트러블슈팅

대시보드 집계 JPQL DTO 직접 프로젝션과 커버링 인덱스를 통한 쿼리 최적화

[배경]

관리자 대시보드 진입 시 전체 매출, 가입 유저 수, 상품 재고, 오늘 주문 건수 등 대량의 데이터에 대한 집계 쿼리가 동시에 실행되어 1,200ms 이상의 누적 지연을 유발했습니다. 특히 조건 컬럼(`status`, `created_at`)을 대상으로 인덱스를 설계하더라도, JPA 기본 호출 특성상 엔티티 전체 컬럼을 로드(Full Scan)하여 디스크 테이블 페이지를 일일이 대조하는 비효율이 컸습니다.

[기술적 의사결정]

디스크 추가 접근을 완벽히 차단하고 메모리 상의 인덱스 트리 스캔만으로 연산을 마치기 위해 Covering Index 설계 및 적용을 핵심 방향으로 잡았습니다. 이를 JPA 환경에서 강제하기 위해 Entity 매핑을 우회하고 필요한 속성만 인덱스 리프 노드에서 퍼올리는 JPQL DTO 생성자 직접 프로젝션(DTO Constructor Projection)을 사용하기로 결정했습니다.

[주요 구현]

  • 복합 인덱스 설계: orders 테이블에 검색/집계 패턴을 결합한 status, created_at, total_price 복합 인덱스 생성
  • JPQL DTO 생성자 프로젝션 적용: JPA에서 SELECT o FROM Order o 대신 `SELECT new com.ecommerce...OrderWidgetDto(SUM(CASE ...), ...)` 와 같이 필요한 데이터 3개 컬럼만 지목하여 인덱스 테이블 조회가 즉각 Covering Index 스캔으로 매핑되도록 구현
  • Soft Delete 결합 인덱스: deleted와 생성 시각 정렬 조건이 반영된 최적 인덱스 분리 선언

[성과]

대시보드 집계 쿼리들이 Full Table Scan에서 Index Range/Fast Full Scan으로 개선되었습니다. 이를 통해 통계 로딩 지연 시간을 1,200ms에서 180ms로 약 85% 단축하여 백오피스 운영 안정성을 획기적으로 개선했습니다.

Hibernate 연관관계 @NotFound 무시 하에서의 Soft Delete NPE 방어 및 가드 로직

[배경]

주문 취소 시 기존에 주문된 상품 정보를 영속화된 관계에서 추적하여 재고를 다시 증설해야 합니다. 그러나 이미 Soft Delete(삭제 처리)된 상품인 경우, `@SQLRestriction("deleted = false")`가 활성화된 Hibernate 프록시 매핑 특성상 연관관계 조인 검색에 차단당해 데이터 로드가 실패하고, 이에 따른 `NullPointerException(NPE)` 또는 `EntityNotFoundException`이 일어나 시스템이 다운될 수 있는 취약점이 감지되었습니다.

[기술적 의사결정]

삭제된 상품 데이터 조회를 위해 별도 Native SQL을 수행하는 비효율을 막고자, 연관 관계 매핑 시 조회 실패를 예외로 처리하지 않는 `@NotFound(action = NotFoundAction.IGNORE)`를 설정했습니다. 또한, 이로 인해 로드 시 해당 필드가 `null`로 매핑되는 환경에 맞춰 서비스 레이어 내에 철저한 Null 검증 가드 로직을 구축하여 NPE를 방어하기로 결정했습니다.

[주요 구현]

  • Hibernate @NotFound 제어: 주문 엔티티 내 Product 연관 필드에 `@NotFound(action = NotFoundAction.IGNORE)`를 매핑해 엔티티 로드 시의 강제 크래시 회피
  • NPE 차단 Guard 조건 적용: 주문 상태 변경 및 취소 시 Product product = order.getProduct(); 이후 상품 객체의 null 여부를 선제 검증하는 `if (product != null && !product.isDeleted())` 구문을 추가해 비정상 참조 흐름을 완벽히 차단
  • 글로벌 공통 예외 규격화: 커스텀 예외 발생 시 프론트엔드가 일관적으로 처리할 수 있도록 CommonException과 글로벌 핸들러 체계를 구축하여 결합도 최소화

[성과]

Soft Delete 처리된 연관 상품의 재고 복구 흐름에서 발생할 수 있는 NPE 발생률을 0%로 통제하고, 어떠한 예외적 사용자 패턴에서도 안정성을 유지했습니다. 더불어 일률적인 ApiResponse 핸들링 구조를 정착시켜 프론트엔드 연동 개발 생산성을 배가했습니다.
