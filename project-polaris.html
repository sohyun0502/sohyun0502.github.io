1. 주제 선정 배경

4인 팀으로 진행한 MSA 기반 AI 루틴 서비스 프로젝트입니다. 사용자가 AI 캐릭터와 함께 일상 루틴을 즐겁게 생성·수행하고, 보상으로 획득한 별조각을 활용해 다양한 아이템을 구매하며 꾸준한 습관 형성을 돕는 서비스를 기획했습니다. 특히 마이크로서비스 간의 통신이 잦은 구조에서, 사용자가 재화를 잃지 않고 언제나 신뢰할 수 있는 안정적인 데이터 정합성 환경을 구축하는 것이 핵심 기술적 목표였습니다.

2. 담당 역할

  • 상점 및 별조각 경제 시스템을 전담하며 분산 트랜잭션 환경에서의 데이터 정합성 확보와 외부 의존성 장애에 대응하는 시스템 복원력 사전 계측 및 검증에 집중
  • 현재 성공적으로 배포 및 실사용 운영 중이며, 실운영 환경에서 발생한 데이터 불일치 및 성능 문제를 운영 로그 기반으로 주도적으로 분석하고 직접 개선

3. 기술 스택

Java / Spring Boot Microservices Architecture gRPC Kubernetes Saga Pattern Outbox Pattern Event Driven Architecture

5. 주요 기능

  • AI 기반 루틴 생성 및 수행: 사용자의 습관 형성을 돕는 맞춤형 AI 대화 및 스마트 루틴 관리
  • 보상 시스템: 매일 루틴 완료 시 별조각(가상 재화) 자동 지급
  • 상점 아이템 구매: 획득한 별조각으로 나만의 캐릭터를 꾸밀 수 있는 아이템 경제 시스템

6. 기술적 의사결정 및 트러블슈팅

Saga · Outbox 패턴 기반의 이기종 서비스 간 Data Interface 안정성 확보

[배경]

[User 서비스] - [Item 서비스] 간 분산 환경 인터페이스(gRPC) 통신 실패로 결제 데이터 불일치가 발생(일 평균 5건)하여, 사용자의 재화(별조각) 유실을 방지하고 데이터 무결성을 보장하기 위한 자동 인터페이스 복구 체계 설계가 필요했습니다.

[기술적 의사결정]

Kafka 클러스터 추가 도입 대신 기존 RDB 인프라를 최대한 활용하여 추가 비용을 최소화하는 Outbox 패턴 인터페이스를 채택하고, 백그라운드 스케줄러 기반의 gRPC 인터페이스 재전송 및 보상 트랜잭션을 구현하여 결과적 정합성(Eventual Consistency)을 보장하기로 결정했습니다.

[주요 구현]

  • State Machine 기반 I/F 상태 관리: 인터페이스 트랜잭션 단계를 PENDING ➡️ COMPLETED / FAILED / REFUNDED 상태로 세분화하여 실시간 모니터링 체계 구축
  • 안정적인 배치 스캔 및 폴링: 활성 트랜잭션과의 충돌 방지를 위해 생성 후 1분 이상 경과한 예외 건을 10초 주기로 스캔하여 복구 개시
  • 지수 백오프(Exponential Backoff) 재시도: 복구 실패 시 재시도 간격을 60초부터 최대 30분까지 2배씩 늘려 시스템 부하를 방지하며 인터페이스 정합성이 맞추어질 때까지 재처리 자동화
  • 멱등성 기반 데이터 이중 오류 차단: 보상 트랜잭션 호출 시 "REFUND_" + idempotencyKey 형태의 고유 멱등키를 활용하여, 네트워크 타임아웃 재시도 시 발생 가능한 이중 환불 등의 데이터 결함 완전 차단
  • I/F 로그 및 운영 알림 구축: 지속적인 실패 건에 대해 정밀 에러 로그를 남기고 시스템 모니터링 알림 체계를 연동하여 즉각적인 운영 조치 프로세스 마련

[성과]

  • 인터페이스 데이터 불일치 건수: **일 평균 5건 ➔ 0건 (100% 개선)**
  • 데이터 유실 오류 완벽 통제로 인한 수동 데이터 복구 및 ITO 운영 공수 제로화

Kubernetes 기반 가상 Mock 서버 및 Chaos Injection을 통한 예외 시나리오 검증

[배경]

외부 AI 서버 의존도가 높은 인터페이스의 지연 응답, 타임아웃 등 다양한 예외 처리 로직의 검증 한계에 직면했으며, 실제 프로덕션 환경에서 발생할 수 있는 간헐적 장애 네트워크 상황을 수동으로 재현 및 검증하는 것이 불가능했습니다. 사전 예외 시나리오 검증 부족 시 외부 인터페이스 장애가 전체 서비스의 이용 실패로 확산될 리스크가 존재했습니다.

[기술적 의사결정]

외부 의존성을 제거하고 독립적인 테스트 시나리오 수행이 가능하도록 Kubernetes 기반의 AI Mock 서버를 구축하고, Header 기반의 Chaos Injection(장애 주입) 아키텍처를 설계하여 다양한 연계 인터페이스 장애 시나리오(지연, 타임아웃, 500 에러)를 반복적으로 재현 및 자동 테스트 체계를 완비했습니다.

[주요 구현]

  • 가상 테스트 환경 격리: Kubernetes 인프라 내에 메인 서비스와 격리된 테스트 전용 AI Mock 서버 Pod 배치
  • 요청 헤더(Header) 기반 장애 유발: 요청 헤더값에 따라 Mock 서버가 동적으로 특정 장애 시나리오를 발생시키는 메커니즘 설계
  • 시나리오 기반 예외 처리 검증: 장애 주입 환경을 활용하여 서킷 브레이커, 재시도(Retry), Fallback 로직의 실제 정상 동작성과 운영 안정성 검증 완료

[성과]

  • 인터페이스 검증 자동화: 외부 서버 의존 없이 독립적·반복적으로 테스트 가능한 예외 시나리오 검증 체계 완비
  • 시스템 복원력 입증: 선제적인 사전 검증을 통해 배포 전 결함을 제거하여 **Fallback 로직 성공률 99.8%, 평균 복구 시간 0.3초 달성**

Application Event 기반 비동기 처리 구조 개선

배경

API 응답 시간 측정 결과, 부가적인 이벤트 로그 수집 모듈의 동기 호출 탓에 핵심 기능인 아이템 구매 API의 평균 응답 시간이 320ms 수준까지 지연되는 성능 저하를 확인했습니다. 또한 이벤트 로그 서비스 장애 발생 시 구매, 로그인 등 메인 핵심 기능까지 연쇄적으로 실패(Cascading Failure)하는 강결합 구조적 문제가 존재했습니다.

기술적 의사결정

초기에는 Kafka 기반 이벤트 처리도 검토했으나, 프로젝트 운영 복잡도를 고려해 Spring의 ApplicationEventPublisher와 @Async 기반의 로컬 비동기 구조를 선택했습니다. 부가적인 인프라 추가 없이 코드 수준에서 도메인 로직과 이벤트 로깅 로직을 완벽히 분리해 내었습니다.

주요 구현

  • ApplicationEventPublisher 기반 이벤트 발행/구독(Pub-Sub) 아키텍처 설계
  • @Async + @EventListener 기반의 스레드 풀 분리 비동기 처리 구현
  • 이벤트 로그 서비스 장애의 전파를 막는 격리(Failure Isolation) 패턴 적용
  • 이벤트 데이터 직렬화 공통 구조 설계로 향후 로깅 스키마 확장성 확보

성과

메인 스레드 블로킹 문제를 해결하여 아이템 구매 API 응답 시간을 320ms에서 180ms로 44% 극적으로 단축시켰으며, 이벤트 로그 서비스 장애 시 핵심 메인 서비스가 실패하는 현상을 완전히 방어(실패율 0%)해냈습니다.
